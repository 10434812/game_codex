## 发现的问题

### 1. P1：Socket.IO 事件缺少参数会抛出未捕获异常

位置：[arena-handler.js](/Users/hh/Desktop/日常开发/锦鲤游戏/back/src/socket/arena-handler.js:53)，另见第 71、77、91 行。

`join_arena`、`leave_arena`、`emote`、`fortune_buy` 的回调直接解构参数，没有默认值和外层异常处理。已登录客户端发送没有参数或参数为 null 的事件，会在权限检查之前抛出 TypeError。

隔离验证直接加载实际模块、注册事件回调，向四个回调分别传入 undefined，四项均抛出 `Cannot destructure property 'sessionId' of 'undefined'`。本地 Socket.IO 的 dispatch 直接调用事件监听器，没有捕获同步异常或异步回调返回的拒绝；在 Node 默认异常处理下有导致后端进程退出的风险。本轮未通过实际网络连接触发进程退出。

建议：入口校验 payload 为普通对象并校验字段，回调统一捕获异常。补充缺参、null 和非法类型的回归测试。

### 2. P1：开局初始化失败后，房间无法恢复或重试

位置：[rooms.js](/Users/hh/Desktop/日常开发/锦鲤游戏/back/src/routes/rooms.js:158)、[room-service.js](/Users/hh/Desktop/日常开发/锦鲤游戏/back/src/services/room-service.js:409)。

`roomService.startGame` 先提交房间 playing 状态和游戏记录，再调用 `gameService.startGameSession` 初始化内存状态及计时器。后一步失败时，路由只返回错误，没有撤销前一步的已提交状态。等待初始化只能让错误到达客户端，不能恢复房间。

隔离验证加载实际路由和 room-service，用内存数据库替身记录状态，在初始化步骤注入异常，结果为：HTTP 500、事务已提交一次、房间仍为 playing；随后重试开局返回 400“游戏已开始”。本轮未使用真实 MySQL 验证事务。

启动时的孤儿会话恢复仅在服务启动时执行，不能及时处理服务运行期间产生的这一状态。

建议：将持久化开局与内存初始化设计为可恢复流程，失败后清理部分内存状态并安全恢复数据库状态，或支持幂等重试初始化。增加初始化失败后的完整流程测试。

### 3. P1：实时通道绕过封禁与注销状态检查

位置：[arena-handler.js](/Users/hh/Desktop/日常开发/锦鲤游戏/back/src/socket/arena-handler.js:36)、[native-arena-ws.js](/Users/hh/Desktop/日常开发/锦鲤游戏/back/src/socket/native-arena-ws.js:121)。

HTTP 鉴权会查询 users 的 `is_banned` 和 `deleted_at`，两个实时入口却只验证 JWT 和 game_players 成员关系。账号被封禁或注销后，只要原 token 未过期且游戏成员记录仍存在，就可继续进入实时通道；已建立连接也没有账号状态重新检查。

Socket.IO 隔离验证使用有效身份的 JWT 替身和返回封禁状态的数据库替身：鉴权成功，鉴权阶段查询数据库次数为 0；加入会话成功，总查询次数为 1，仅查询 game_players，没有查询封禁状态。原生 WebSocket 的同类遗漏通过代码核查确认，未执行网络复现。

建议：HTTP 和两个实时入口共用账号有效性检查；明确封禁、注销后现有连接的失效机制。

### 4. P2：开局玩家信息查询错误绑定数组参数

位置：[game-service.js](/Users/hh/Desktop/日常开发/锦鲤游戏/back/src/services/game-service.js:212)、[db.js](/Users/hh/Desktop/日常开发/锦鲤游戏/back/src/models/db.js:44)。

查询使用 `WHERE id IN (?)`，参数为 `[userIds]`，但数据库 helper 使用 mysql2 的 `pool.execute` 预编译接口，不会把数组展开为多个 SQL 占位符。

已调用项目本地安装的 mysql2 3.22.3 参数编码器验证：`[1]` 被编码为一个 JSON 参数 `"[1]"`，`[1,2]` 被编码为一个 JSON 参数 `"[1,2]"`，类型编号为 245。它们不是独立的整数参数列表，无法按预期匹配全部玩家。

如果实际数据库未返回对应用户，当前逻辑会把姓名退化为 `Player`、头像退化为空字符串。数据库具体返回结果或错误取决于服务端转换行为，本轮没有实际 MySQL 查询证据，不将其表述为已在线复现的开局失败。

建议：按玩家数量生成 `IN (?, ?, ...)`，传入平铺参数，并处理空玩家列表。现有数据库 mock 不检查实际驱动绑定行为，因此测试通过不能排除此问题。
